# Unilabs Supabase database

This directory contains the versioned database changes and regression tests for the Unilabs AI Appointment Demo.

- `20260818081423_appointment_platform_hardening.sql`
- `20260818081433_demo_scenario_automation.sql`

All three migrations are applied to Supabase project `mshxmttxwfkvexchwjkr`.

## Current design

Supabase remains the source of truth for locations, rooms, appointment slots, patients, appointments, waitlists, notifications, and events. It does not choose the customer communication channel.

A waitlist offer now creates exactly one channel-neutral notification payload. Talkdesk and the Vercel integration layer decide whether that offer is delivered through Chat or Voice and how it is phrased.

The earlier `patient_channel_identities` table was removed because patient/channel mapping is not required in the database for the current demo use cases.

## Active demo scenario

The baseline is generated by:

```sql
select public.reset_demo_scenario(
  (now() at time zone 'Europe/Amsterdam')::date + 1,
  7,
  5
);
```

This creates seven calendar days for Amsterdam, Rotterdam, and Utrecht, with nine hourly slots per location and day. The 12:00 slot remains non-bookable. The reset restores the central Patient A / Patient B story, existing appointment and waitlist scenarios, background capacity, sequences, notifications, events, and idempotency state.

The reset removes all previous demo scenario rows and recreates one `default` scenario, so the baseline is deterministic.

## Main RPCs

Channel-neutral read RPC:

- `check_availability`

Idempotent write RPC overloads requiring `request_id`:

- `book_appointment`
- `join_waitlist`
- `reschedule_appointment`
- `cancel_appointment`
- `decline_waitlist_offer`

Operational RPCs:

- `reset_demo_scenario`
- `expire_waitlist_offers`

Legacy overloads remain temporarily available so the existing Vercel endpoints continue to work until the integration layer is updated.

## Simplified state

`action_requests` now stores only the request identity, payload hash, completed response, and timestamps. The unused durable `failed` state was removed.

`demo_scenarios` now stores only the scenario date, generated day count, offer hold time, and reset timestamp.

`notifications` now stores only one channel-neutral waitlist notification per offered waitlist entry:

- `notification_id`
- `patient_id`
- `waitlist_entry_id`
- `status`
- `created_at`
- `payload`
- `responded_at`

Notification status is limited to `pending`, `responded`, `cancelled`, or `expired`.

## Waitlist lifecycle

An offered slot is reserved through `offer_token` and `offer_expires_at`. The `unilabs-expire-waitlist-offers` cron job runs every minute and forwards expired capacity to the next waiting patient.

Cancelling an appointment now also closes any active waitlist entry that depends on that appointment. If this releases an offered reservation, the slot is offered to the next waiting patient.

## Security

Application migrations are owned by `postgres`. Default table, sequence, and function privileges for that owner grant access only to `postgres` and `service_role`.

`PUBLIC`, `anon`, and `authenticated` have no `USAGE` or `CREATE` privilege on the `public` schema, and current application RPCs explicitly deny execution to those roles.

Supabase-managed default privileges for the internal `supabase_admin` role cannot be changed by the project database owner. No workaround is used; the application relies on explicit grants/revokes for its own objects and on the restricted schema ACL.
